## 0. 摘要：读者只有 3 分钟

**这个工具到底在干什么？** 一句话：**用 PC 冒充索尼的「PlayMemories Camera Apps」商店服务器，让相机自己下载并安装 APK。**

原项目最容易误解的一点必须先纠正：

> **它并不是"启动一个本地 HTTPS 服务器，然后等相机连上来"。**

真实机制是：PC 通过 USB（PTP/MTP）让相机打开一个**代理 socket**，相机把要发给商店的**原始 TLS 字节流**原样塞进 USB 报文交给 PC，PC 在本地扮演 TLS 服务端完成握手，然后**把 HTTP 响应伪装成 TLS 记录**再通过 USB 送回相机。整个过程中：

- 相机没有走网络，**没有 WiFi、没有 DNS 劫持、没有 hosts 修改**；
- 那个"本地 HTTPS 服务器"实际监听在 `127.0.0.1:4443`，但**相机的 `SslStartMessage` 里报告的 host/port 被直接忽略**（`pmca/installer/__init__.py:83` 注释 `# Ignoring message.host`），PC 只会连自己配的地址；
- 所以**端口号是无关紧要的**，这也解释了为什么 `LocalMarketServer` 的 url 是 `https://127.0.0.1/`（不带端口）而相机照样工作——它根本不解析这个 URL。

**五个"必须先知道"的事实**（都是踩过坑才发现的）：

| # | 事实 | 后果 |
|---|---|---|
| F1 | 相机**要求证书链能链到内置受信根 CA**，但不校验有效期/吊销/主机名 | **不能用自签证书**；必须原样继承那张 2012 年过期的 `*.localtest.me` COMODO 证书（含私钥） |
| F2 | 相机客户端是 2011–2012 年的 TLS 栈，原项目**显式锁定过 TLS 1.0**，且因 SHA-1 中间证书被 OpenSSL 拒绝而**整栈换成了纯 Python 的 tlslite-ng** | **rustls 很可能直接握手失败**；首选 `openssl` crate + `ALL:@SECLEVEL=0` |
| F3 | JSON 响应必须**谎报 `Content-Type` 为 SPK 的 MIME**（原注释："This is not quite correct, it should be 'application/json', but it only works that way"） | 最容易踩的一个格式坑 |
| F4 | SPK 容器用的 AES 密钥**可以从一个硬编码常量直接推出**：`c301afd22ddba4c090eca46258e4bfb1`（已用 Python 独立复算 + 与 Rust 输出逐字节比对验证，见 §2.6 的更正说明） | **Rust 侧完全不需要 RSA 实现**，比 Python 版更轻 |
| F5 | 安装主链路上**不涉及 PC 文件系统路径**——相机是通过 USB 报文拿数据的 | "中文路径问题"只存在于选文件/缓存/配置/日志这几个本地环节，Rust 默认就对 |

**三个最高风险点（必须在写业务代码前先用实验打掉）**：

| # | 风险 | 影响 | 对策 |
|---|------|------|------|
| R1 | 相机的 TLS ClientHello 只支持 TLS 1.0 / 不支持 SNI / 只提供静态 RSA 密钥交换，而现代 TLS 库默认全部拒绝 | 整个安装流程走不通 | 第一步就抓 ClientHello 原始字节（§9 阶段 0），据此在 rustls / openssl / 手写 TLS 之间定方案 |
| R2 | Windows 上相机被 `WPD`/`USBSTOR` 驱动占用，`nusb`/WinUSB 打不开设备 | 要么要求用户装驱动（体验灾难），要么得写原生后端 | Windows 优先做**免驱**双后端：SCSI Pass-Through（MSC）+ WPD COM（MTP），详见 §11 D1 |
| R3 | 服务模式的 senser 认证用的是**带 bug 的 SHA-1**（`len & 0x1f`） | 若做服务模式则认证必然失败 | 本期不做服务模式；将来做时不能直接用标准 `sha1` crate（§4.10） |

**给用户的一句话承诺**：新项目里，"中文路径问题"**不会出现在安装主链路上**；它会出现在 **APK 文件选择、下载缓存、配置与日志** 这几个本地环节，而 Rust 在这几处**默认就是正确的**——只要守住 §7 列出的 11 个检查点。

## 1. 项目定位与范围

### 1.1 目标（本期）

做一个**单一用途、开箱即用、全中文、Windows 优先**的桌面应用：

> 插上相机 → 点一下 → APK 装进相机。

### 1.2 明确不做（本期）

- 固件升级 / updater 模式（需要另一套 MSC 协议与 fdat 负载，工作量大且风险高）
- 服务模式（senser，需要用户装 libusb 驱动，与"开箱即用"冲突）
- 相机设置 tweak / 备份 / GPS 数据 / WiFi / 直播配置
- macOS（依赖索尼私有 kext，无替代路径且无法离线验证）
- 从**官方商店**下载 APK（需要用户的 `portalid` 登录态，违背"开箱即用"）

以上都保留为**后续可插拔的"扩展模式"**，架构上留出接口（§5）。

### 1.3 为什么值得从 Python 重写到 Rust

| 维度 | 原项目（Python + tkinter） | 新项目（Rust + Iced） |
|---|---|---|
| 启动 | PyInstaller onefile，启动时解压到临时目录，冷启动秒级~十秒级 | 原生 exe，目标冷启动 < 300 ms |
| 体积 | 内含 Python 运行时 + Crypto + tlslite，数十 MB | 目标单 exe ≤ 12 MB |
| 中文界面 | tkinter 默认字体渲染中文发虚，需手动指定字体 | 系统字体（微软雅黑）原生清晰 |
| Unicode 路径 | 依赖 `locale`/`fsencode`，跨平台行为不一致 | UTF-8 字符串 + 原生宽字符 API，默认正确 |
| 依赖链 | pyusb/libusb 二进制 + tlslite + pycryptodome + comtypes/pywin32 | 纯 Rust 静态编译（TLS 走 vendored openssl），无 DLL 依赖 |
| UI 流畅度 | tkinter 主线程阻塞风险、进度更新卡顿 | Iced 渲染线程与业务线程天然分离 |
| 维护 | 2015 年代码，Py2/Py3 兼容残留，CI 还跑在 Python 3.6 | 类型系统约束协议字节解析 |

## 2. 原项目分析（模块地图）

### 2.1 全局架构：八层会话模型

这是理解原项目最重要的一张图。**它们是层层嵌套的信封**，移植时必须一层不漏地复刻：

```
┌─ L8 业务 UI ────────────  pmca-gui.py (tkinter) / pmca-console.py (CLI)
│                           InstallerFrame「Install selected app」按钮
├─ L7 安装编排 ───────────  pmca/commands/usb.py::installApp()
│                           + pmca/installer/__init__.py::install()  ← 状态机主循环
├─ L6 商店协议 ───────────  HTTP/REST over USB：/task/start、/task/progress、/task/complete
│                           JSON actions: {"command":"dlandinstall","args":<url>}
├─ L5 TLS ───────────────  tlslite 服务端握手 + LocalMarketServer 的 HTTP 语义
├─ L4 代理隧道 ───────────  SONY_MSG_Tcp：ProxyConnect / ProxyData / ProxyEnd / ProxyDisconnect
├─ L3 索尼消息协议 ───────  SonyAppInstallCamera：Common(0x400/0x401/0x402)、Tcp(0x5xx)、Rest(0/2)
├─ L2 PTP 代理消息 ───────  SendProxyMessageInfo(0x948c)/SendProxyMessage(0x948d)/Get(0x9488/0x9489)
├─ L1 MTP/PTP 与 MSC ────  Windows：WPD(COM) 或 SCSI Pass-Through；其他：libusb 裸传输
└─ L0 USB 设备 ──────────  VID 0x054c 的索尼设备枚举与模式识别
```

新手最容易踩的坑：**L6 和 L5 是两条并行的通道，不要混为一谈。**

- **L6（REST 通道）**：相机 ↔ PC 的**控制通道**。用 `SONY_MSG_Rest` 信封包裹 HTTP 风格的文本（`POST /task/start REST/1.0`）。PC 侧由 `installer.install()` 解析并路由，**不经过** LocalMarketServer。
- **L5（TCP/TLS 隧道）**：相机把**真正的 TLS 字节**塞进 `SONY_MSG_Tcp_ProxyData` 交给 PC，PC 把它灌进 TLS 服务端，服务端的 HTTP 响应字节再原路回灌。相机以为自己在和 `www.playmemoriescameraapps.com` 说话。

**关键点 1：真正的"驱动工厂"不在 `usb/driver/__init__.py`，而在 `pmca/commands/usb.py:133-172` 的 `importDriver()`。** 它在 Windows 上同时注册两套后端（原生 MSC+WPD，外加 libusb 作为补位），见 `commands/usb.py:163-168`，那几行布尔表达式是刻意写成"Windows 上 always true"的。

**关键点 2：设备模式识别不是靠 VID/PID，而是靠 PTP DeviceInfo 字符串 + 支持的 OperationCode 集合**（`usb/sony.py:37-64`）：

```python
# sony.py:47-54  普通 MTP 相机（ExtCmd 可用）
operations = {0x9280 /*SonyDiExtCmd_write*/, 0x9281 /*read*/, 0x9282 /*SonyReqReconnect*/}
return info.manufacturer == 'Sony Corporation' and info.vendorExtension == '' \
       and operations <= info.operationsSupported

# sony.py:56-64  App 安装模式相机
operations = {0x9488, 0x9489, 0x948c, 0x948d}
return info.manufacturer == 'Sony Corporation' \
       and 'sony.net/SEN_PRXY_MSG:' in info.vendorExtension \
       and operations <= info.operationsSupported
```

**关键点 3：枚举→分类→yield 的统一入口是 `commands/usb.py:175-217 listDevices()`**：

```
MSC(类8)  → MscDevice.getDeviceInfo() → manufacturer=='Sony' && model in ['DSC','Camcorder']
            ├─ idProduct in [0x033a, 0x03e2]  → SonyMscUpdaterDevice    (updater 模式)
            └─ 否则                            → SonyMscExtCmdDevice     (普通 MSC)
PTP(类6)  → MtpDevice.getDeviceInfo() → isSonyMtpCamera            → SonyMtpExtCmdDevice       (普通 MTP)
                                        isSonyMtpAppInstallCamera  → SonyMtpAppInstallDevice  (安装模式)
Vendor(255)→ idProduct in [0x02a9, 0x0336]                          → SonySenserDevice         (服务模式)
```

其中 `SONY_ID_VENDOR = 0x054c`、`SONY_ID_PRODUCT_UPDATER = [0x033a, 0x03e2]`、`SONY_ID_PRODUCT_SENSER = [0x02a9, 0x0336]`（`usb/sony.py:29-34`）。

**关键点 4：字节序不统一，且没有 TLV**。全是定长 `struct` + 显式 `dataSize` 字段：

- 小端：`InfoMsgHeader`(PTP 代理)、`_BaseSonyMscExtCmdDevice` 的 ExtCmd 头、`SenserPacketHeader`、Updater 包 22 字节头
- 大端：`CommonMsgHeader`、`MsgHeader`、`TcpMsgHeader`、`RestMsgHeader`、AuthPacket

**接收时必须按报文里的 `dataSize` 截断，不能按实际收到的字节数处理**（USB 会把缓冲补齐）。这是移植期最容易产生"偶发随机崩溃"的地方。

### 2.5 LocalMarketServer —— 本地"假商店"

**这是文档里最需要被正确理解的一个模块。** 它由三个小文件构成：

| 文件 | 行数 | 关键内容 |
|---|---|---|
| `marketserver/server.py` | 108 | `LocalMarketServer(TCPServer)`：`127.0.0.1:4443`，**tlslite 手工 TLS**，`serve_forever()` 跑在 daemon 线程 |
| `marketserver/__init__.py` | 62 | XPD 生成、JSON 响应生成、相机上报数据解析 |
| `marketserver/constants.py` | 6 | `baseUrl = 'https://www.playmemoriescameraapps.com/'` |

**它的 HTTP 语义极其简陋**（`server.py:28-95`）——**根本没有路由**：

```python
def do_POST(self):
    # 唯一的 POST 处理：收到相机上报的 JSON → 存起来 → 回一个 JSON
    self.server.handlePost(self, self.rfile.read(int(self.headers['Content-Length'])))

def handlePost(self, handler, body):
    if not self.result and self.apk:
        response = getJsonInstallResponse('app', self.url)   # 命令相机去下载
    else:
        response = getJsonResponse()                          # 空 actions = 结束
    self.result = parsePostData(body)                         # 保存相机上报的数据
    handler.output(constants.jsonMimeType, response)

def handleGet(self, handler):
    # 唯一的 GET 处理：把 APK（打包成 SPK）吐给相机
    handler.output(spk.constants.mimeType, spk.dump(self.apk), 'app%s' % spk.constants.extension)
```

**注意这个"状态机"的巧妙与脆弱**：它用 `self.result`（是否有过上报）和 `self.apk` 两个变量实现"第一次 POST 下令安装，之后 POST 一律回空"。整个安装流程只有**一次** POST 上报，所以逻辑能跑通。

**三个必须一起移植的常量/格式**：

1. **XPD 文件**（`xpd/__init__.py`）：INI 文本，节名 `[DrmTCD]`，三个键：
   - `TCD` = 目标 URL（这里被设为 `https://www.playmemoriescameraapps.com/`）
   - `TKN` = `'0'`（correlation id）
   - `CIC` = `HMAC-SHA256(key=cicKey, msg=TCD).hexdigest()`（`xpd/__init__.py:35-37`）
   - MIME 类型 `application/x-psn-dstartup2`；`cicKey` 是 **45 字节**硬编码密钥（`xpd/constants.py:5`，90 个十六进制字符；早期误记为 60 字节），逆向自 `libscalaramarket-jni.so` / `libjniusbdluser.so`）
2. **安装指令 JSON**（`marketserver/__init__.py:49-58`）：
   ```json
   {"actions":[{"command":"dlandinstall","args":"https://127.0.0.1/","attrs":[{"attrname":"appname","attrvalue":"app"}]}]}
   ```
3. **MIME 类型陷阱**（`marketserver/constants.py:5-6` 注释原文）：
   > `# This is not quite correct, it should be 'application/json', but it only works that way`
   > `jsonMimeType = spk.constants.mimeType` → `'application/vnd.sony.spk.package-archive'`

   **回复 JSON 时必须谎报 Content-Type 为 SPK 的 MIME，否则相机不认。** 这种"反直觉但必须照抄"的细节正是重写项目最大的坑源。

**证书文件 `certs/localtest.me.pem` 的独立解析结果（我用 .NET X509 + DER 解析的真实字段）**：

```
[私钥]  RSA 2048 bit, e = 65537（与叶证书模数一致，n 以 be26dc6c12822460… 开头）
[证书1] CN=*.localtest.me, OU=EssentialSSL Wildcard, OU=Domain Control Validated
        Issuer : CN=EssentialSSL CA, O=COMODO CA Limited, …（COMODO 签发）
        NotBefore / NotAfter : 2012-05-17 → 2013-05-17   ← 已过期十余年
        SigAlg : sha1RSA        PublicKey : RSA 2048 bit
        SAN    : DNS:*.localtest.me, DNS:localtest.me
[证书2] CN=EssentialSSL CA  ←  CN=COMODO Certification Authority（根，相机内置受信）
        SigAlg : sha1RSA        NotAfter : 2019-12-31     CA:TRUE
```

文件里**同时包含私钥和证书链**（PEM: `RSA PRIVATE KEY` + 2 个 `CERTIFICATE` 块），`server.py:50-54` 分别解析。域名是 `localtest.me` 而商店是 `playmemoriescameraapps.com`，且证书 2013 年就过期——但相机依然接受。

> ⚠️ **但不要据此认为"相机零校验"**：权威文档 `docs/AppInstallation.md:26` 明确写了相机**要求证书链能链到内置受信根 CA**，只是不校验"有效期 / 吊销 / 主机名"这三项。**准确结论见 §4.4**（这一条是我在写作中推翻自己初判的地方）。
>
> 另外，这张证书之所以能公开流传，是因为 `localtest.me` 的通配符解析到 `127.0.0.1`、且其私钥是**公开**的（`readme.localtest.me`）——一张"**真 CA 签发、但私钥人人都有**"的证书。**这是整个方案的基石，不可替换为自签。**

**SPK 容器格式（`spk/__init__.py:16-24, 46-63`）**：

```
offset 0   : magic      '1spk'              (4B)
offset 4   : keyOffset  uint32 LE           (固定 0)
offset 8   : keySize    uint32 LE           (256)
offset 12  : encryptedKey                    ← RSA 密文，固定复用同一段 blob
offset 12+keySize : encryptedData            ← APK 的 AES-128-ECB 密文（分块）
```

**加密细节（这是全文最有价值的一段，因为它让 Rust 侧可以彻底不依赖 RSA 大数运算）**：

- `dump()`：`encryptedKey` 直接使用硬编码常量 `sampleSpkKey`（256 字节，从官方 `TouchLessShutter100.1.spk` 偏移 `0x0C` 处抄出来的），**不需要自己加密**；`key = decryptKey(sampleSpkKey)` 才是真正要用的 AES 密钥。
- `decryptKey()`（`spk/__init__.py:65-72`）：是**教科书式原始 RSA**（无 OAEP、无 PKCS#1 v1.5 填充）——即 `m^d mod n`。
- **我独立复算了这条链**：用 `spk/constants.py` 的 `rsaModulus`/`rsaExponent=65537` 对 `sampleSpkKey` 做原始 RSA 解密（`pow(blob, 65537, n)`）。
  解出来的是一个 **256 字节**的值，但它的**最高 240 字节全为 0**，真正的密钥是**最低 16 字节**：

  ```
  AES-128-ECB key = c301afd22ddba4c090eca46258e4bfb1
  ```

  ⚠️ **这里有个坑，记录在此以免后人重踩**：
  解出的 256 字节结果里，**密钥在最后 16 字节，不在前 16 字节**。
  我第一版推导用了 .NET `BigInteger`，把偏移搞错，得出 `8c6d0be5e0a75c40dbee68f8a8ed3f24`
  这个**错误值**，还一度写成"已经复算确认"。
  实际上 `8c6d0be5…` 是那个 256 字节结果的**第 12–27 字节**，属于中间垃圾，无任何含义。

  **终局确认方式（已执行）**：我用 Python 独立实现了一遍 SPK 打包，
  与 Rust 实现对同一个输入文件产出的 SPK **逐字节完全一致**
  （3000 字节输入 → 3276 字节 SPK，FNV-1a 指纹均为 `3854cb10e657d532`）。
  两条独立实现得到同一结果，比"看代码推导"可靠得多。

  → **新项目可以直接硬编码这 16 字节，完全不需要引入 RSA 库。** 这是 Rust 版比 Python 版更轻的一个具体例子。
  （Rust 侧另有 `fixed_aes_key_fingerprint` 测试，用 FNV-1a 指纹锁住这个常量，改错会立刻失败。）
- `encryptData()`（`spk/__init__.py:79-82`）：`AES-128-ECB`，**按 1 MiB 分块**（`blockSize = 0x100000`），每块**独立补 PKCS#7**（`paddingSize = 16`），因此**密文块大小 = 1 MiB + 16 B = 0x100010**。⚠️ **分块独立补齐这一点必须严格照抄**（写错就 AES 块错位，相机解不出来）。块大小是 16 的倍数，所以每块的填充永远是完整的 16 字节。
- 文件名与 MIME：`extension = '.1.spk'`、`mimeType = 'application/vnd.sony.spk.package-archive'`。

**APK 校验（`commands/usb.py:88-110`）**：解析包名/版本/versionCode/`minSdkVersion`，**`minSdkVersion > 10` 只打印警告不阻断**（相机是 Android 2.3.7，对应 API 10）。主机侧**不校验签名、不比对包名版本**；真正的校验在相机端（`packages.xml` 的 cert index）。新项目应把 minSdk 警告升级为**明确的 UI 警告条**而不是日志。

### 3.1 详细时序（对应 `installer/__init__.py::install()` 的主循环）

```
[P0] UI → HOST : installApp(apkPath)
     HOST : 读取 APK → 解析 AndroidManifest（包名/版本/minSdk）
            → 若 minSdk>10 记一条 UI 警告（原项目仅打印）
     HOST : spk = dump_spk(apk)                    # magic '1spk' + 固定 key blob
            + AES-128-ECB 按 1 MiB 分块、每块补 PKCS#7（密文块 0x100010）
     HOST : 启动 TLS 服务端，绑定 127.0.0.1:0（端口可随机，见 §4.5）
     HOST : xpd = "[DrmTCD]\nTCD = https://www.playmemoriescameraapps.com/\n
                    TKN = 0\nCIC = <HMAC-SHA256(cicKey, TCD)>\n"

[P1] HOST → USB : 枚举 VID=0x054c
     HOST : 读 DeviceInfo，判定模式：
              vendorExtension == '' 且支持 {0x9280,0x9281,0x9282} → 普通 MTP（可安装）
              属于 AppInstall 特征                                   → 已在安装模式
              两者皆非                                              → UI 提示"请切到 MTP/存储模式"

[P2] HOST → CAM : DevInfoSender.GetModelInfo          (SONY_CMD_DevInfoSender_GetModelInfo  = (1,1))
     CAM  → HOST: 机型名、型号代码、固件版本
     HOST → CAM : ScalarExtCmdPlugIn.NotifyScalarDlmode (5,2)，readBufferSize = 0
     CAM : 相机侧重启 USB 子系统（屏幕会提示不要断开）
     HOST : 关闭当前设备句柄

[P3] HOST : 每 500 ms 重新枚举，最多 10 次（5 秒窗口）
            直到发现 1 台 SonyAppInstallDevice（vendorExtension 含
            'sony.net/SEN_PRXY_MSG:' 且支持 {0x9488,0x9489,0x948c,0x948d}）
     HOST : 超时 → UI 提示「请在相机上确认后重试」（不 panic，可重入）

[P4] HOST : dev.emptyBuffer()                     # 收完所有残留消息直到 receive() 返回 None
     HOST → CAM : SONY_MSG_Common_Start(0x400)
                  body = numProtocols=2 + [('TCPT',0x01), ('REST',0x100)]

     CAM  → HOST: SONY_MSG_Common_Hello(0x401)
                  body = numProtocols + [(name,id),...]
     HOST : 校验协议表中存在 TCPT 与 REST

[P5] HOST → CAM : SONY_MSG_Rest(type=SONY_MSG_Rest_Out=2)
                  body = 真·HTTP 文本（CRLF）：
                    POST /task/start REST/1.0\r\n
                    Content-type: application/x-psn-dstartup2\r\n
                    \r\n

     CAM  → HOST: ResponseMessage（type=2 表示 camera→host 的 REST 出站）
                  body = HTTP 响应文本：
                    REST/1.0 200 OK\r\n ... \r\n\r\n {"resultCode":0,"message":"..."}

[P6] CAM  → HOST: SONY_MSG_Tcp_ProxyConnect(0x501)，带 socketFd、host、port
     ※ HOST 完全忽略 host/port（原实现注释 "Ignoring message.host"）
     HOST : 连接自己配置的本地地址，建立 TLS 服务端状态机
     HOST → CAM : SONY_MSG_Tcp_ProxyData(0x503)（承载 TLS ServerHello..Finished）

     ── 以下所有内容都在「USB 报文 → TCP 隧道」里双向搬运 ──
     CAM  → HOST: 0x503，data = TLS ClientHello 原始字节
     HOST : 状态机吃入，产出 ServerHello/Certificate/...，用 0x503 回灌
     ... (握手往返若干轮) ...
     HOST : 握手完成，得到明文通道

[P7] CAM  → HOST: 隧道内 HTTPS：POST / （Content-Length: N，body=设备上报 JSON）

     HOST : 把相机上报的 JSON 存下来（后面用作结果）

[P8] CAM  → HOST: 隧道内 HTTPS：GET /   ← 相机开始下载 SPK
     HOST → CAM : 200 OK
                  Connection: Keep-Alive
                  Content-Type: application/vnd.sony.spk.package-archive
                  Content-Length: <spk 总长>
                  Content-Disposition: attachment;filename="app.1.spk"
                  \r\n
                  <SPK 二进制，按 TLS 记录分片，经 USB 0x503 消息搬运（通常 16 KiB/包）>
     HOST : 每次搬运累加进度 → UI 进度条（换算成 SPK 总字节的比例）

[P8'] 期间相机可能经 REST 通道上报进度：
     CAM  → HOST: SONY_MSG_Rest_In(0) → POST /task/progress
                  {"status":<n>,"status text":"...","percent":<p>,"total size":<t>}
     HOST : 优先用 percent 刷新 UI（比字节比例更权威）

[P9] CAM : 相机侧：SPK 解密 → 得 APK → 调用包管理器安装 → 启动应用
     （此阶段 HOST 只在隧道里被动响应，不需要发指令）

[P10] CAM → HOST: SONY_MSG_Rest_In(0) → POST /task/complete
                   {"resultCode":<code>,"message":"..."}
      HOST → CAM: SONY_MSG_Common_Bye(0x402)
                   body = ThreeValueMsg(a=0,b=0,c=0)
      HOST : 关 TLS、关本地监听、清理线程
      HOST → UI : 成功 / 失败 + 相机的原始 message
```

### 3.2 三个"必须照抄"的协议怪癖

1. **忽略主机名与端口**：`installer/__init__.py:83` 的 `# Ignoring message.host`。相机上报的 host 是它以为要连的商店域名，PC 必须无视它，连自己配的本地地址。
2. **JSON 谎报 MIME**：`Content-Type` 必须是 SPK 的 MIME 才能被相机接受（`marketserver/constants.py:5-6` 注释明说了"这不对，但只有这样才行"）。
3. **"第一次 POST 下令、之后 POST 一律回空"**：商店端状态机用 `result`/`apk` 两个变量实现，第二次 POST 必须返回 `{"actions":[]}`，否则相机会重复安装。

**另外两条重要语义**（容易误解）：

4. **PC 全程不主动重启相机**——装完后是**相机自己重启**生效。`SonyExtCmdCamera.powerOff`（`sony.py:340`）在全仓库**没有任何调用点**。
5. **不需要任何 DNS / hosts / 代理劫持**——唯一的"劫持点"是 USB 代理层（见怪癖 1）。

### 3.3 原实现的三个薄弱点（新项目应改进）

| 薄弱点 | 原实现 | 风险 | 新项目方案 |
|---|---|---|---|
| 主循环忙等 | `while True: message = dev.receive(); if None: continue`（无 sleep） | 空转吃满一个 CPU 核，笔记本风扇狂转 | 用阻塞式 USB 读 + 事件通知，空闲时零占用 |
| 假握手 + 单连接 | 真开一个本地 socket，且只保存一个 `connectionId`/`sock` | 相机开第二条连接即崩；受端口占用影响 | 直接对接内存状态机（§5.2），用 `HashMap<conn_id, TlsSession>` 支持多路 |
| 错误处理粗糙 | 裸 `Exception`、`except:` 吞异常（`usb.py:296-297`） | 用户只看到一句话，无法诊断 | 结构化错误 + 可重试性标注 + 中文"怎么办"提示（§4.11） |

## 4. 需要重新实现的关键协议与逻辑清单

> 标注：★ = 必须逐字节一致；☆ = 语义一致即可，实现自由；⚠️ = 有坑。

### 4.1 USB 设备发现与分类 ☆

| 项 | 值 |
|---|---|
| 厂商 ID | `0x054C`（Sony） |
| updater 模式 PID | `0x033A`, `0x03E2` |
| 服务模式 PID | `0x02A9`, `0x0336` |
| MSC 判定 | `manufacturer == 'Sony'` 且 `model ∈ {'DSC','Camcorder'}` |
| MTP 普通模式判定 | `manufacturer == 'Sony Corporation'` 且 `vendorExtension == ''` 且支持 `{0x9280,0x9281,0x9282}` |
| MTP 安装模式判定 ★ | `manufacturer == 'Sony Corporation'` 且 `'sony.net/SEN_PRXY_MSG:' in vendorExtension` 且支持 `{0x9488,0x9489,0x948C,0x948D}` |
| 约束 | 必须支持"有且仅有一台设备"的语义；多台要明确报错而不是随机挑一台 |

**⚠️ 陷阱**：`vendorExtension` 是 PTP `GetDeviceInfo` 响应里的字符串，不是 USB 描述符。必须先把 MTP 层打通才能做分类。

### 4.2 MTP 代理消息层（PTP 容器 + 索尼私有 OperationCode）★★★★

这是整个移植里**最硬的一块**，也是最容易做对的一块（纯字节操作）。

```
PTP 操作码（App 安装模式）：
  PTP_OC_GetProxyMessageInfo  = 0x9488   # 读：索取"下一条消息"的元信息
  PTP_OC_GetProxyMessage      = 0x9489   # 读：索取消息体
  PTP_OC_SendProxyMessageInfo = 0x948C   # 写：声明"我要发一条消息"
  PTP_OC_SendProxyMessage     = 0x948D   # 写：发消息体
  PTP_OC_GetDeviceCapability  = 0x940A

PTP 响应码：
  PTP_RC_NoData          = 0xA488   # "暂时没有数据"（正常返回，不是错误！）
  PTP_RC_SonyDeviceBusy  = 0xA489   # 忙 → 必须重试
  PTP_RC_InternalError   = 0xA806
  PTP_RC_TooMuchData     = 0xA809

InfoMsgHeader（小端，共 58 字节）：
  offset 0  : uint32  0x00010000(读时) / 0x00000000(写时)
  offset 4  : uint16  magic = 0xB481
  offset 6  : uint16  0
  offset 8  : uint32  dataSize        ← 必须用它截断后续消息体
  offset 12 : uint16  0x3000(读时) / 0x0000(写时)
  offset 14 : 42 字节 填充

MsgHeader（大端，2 字节）：uint16 type
  0 = Sony 通用消息（Common）
  1 = TCP 代理消息
  2 = REST 消息
```

**发送流程（`usb/sony.py:621-632`）★**：

```
1) 构造 info = InfoMsgHeader(magic=0xB481, dataSize=len(payload))，其余字段置 0
2) 循环：response = SendProxyMessageInfo(cmd=[], data=info)
        直到 response != PTP_RC_SonyDeviceBusy
3) 循环：response = SendProxyMessage(cmd=[], data=payload)
        直到 response != PTP_RC_SonyDeviceBusy
4) 检查 response 是否为成功码 0x2001
```

**接收流程（`usb/sony.py:634-643`）★**：

```
1) (rc, data) = GetProxyMessageInfo(args=[0])     # 参数固定为 0
   ⚠️ data == b'' 且 rc == 0xA488 时表示"当前无消息"，返回 None，调用方继续等
2) 校验 data 里的 magic == 0xB481，读出 dataSize
3) (rc, data) = GetProxyMessage(args=[0])
   允许 rc ∈ {0x2001, 0xA488}；若 0xA488 则返回 None
4) 返回 data[0 .. dataSize]        ★ 必须按 dataSize 截断
```

**⚠️ 四个致命细节**：
- 忙码 `0xA489` 是**无限重试**（原实现 `while` 无上限、无退避）。新项目应加"指数退避 + 总超时"，否则相机死机时 UI 会永久卡死。
- `PTP_RC_NoData(0xA488)` 是**正常状态**（无消息），不能当错误抛出。
- `dataSize` 是唯一可信的长度来源。按实际收到的字节数处理会读到 USB 缓冲的垃圾。
- 同类忙重试在 MSC 侧是 sense 码 `(0x9, 0x81, 0x81)`（`sony.py:92-95`），Updater 侧则是另一套状态码。

### 4.3 索尼消息信封层（Common / TCP / REST）★

```
CommonMsgHeader（大端，16 字节）：
  uint16 version = 1
  uint32 type
  uint32 size        ← 从本头起始算起的整条消息长度（含头）
  uint8[6] 填充

外层 type（MsgHeader.type）：
  0 = SONY_MSG_Common
  1 = SONY_MSG_Tcp
  2 = SONY_MSG_Rest

Common 子类型：
  0x400 = Common_Start   (host→cam：声明协议表)
  0x401 = Common_Hello   (cam→host：返回协议表)
  0x402 = Common_Bye     (host→cam：结束)

TcpMsgHeader（大端，4 字节）：int32 socketFd
Tcp 子类型：
  0x501 = Tcp_ProxyConnect    (cam→host)  body: uint16 port + int32 hostSize + host
  0x502 = Tcp_ProxyDisconnect (cam→host)
  0x503 = Tcp_ProxyData       (双向)      body: int32 size + bytes
  0x504 = Tcp_ProxyEnd        (host→cam)  body: ThreeValueMsg(a=1,b=1,c=0)

RestMsgHeader（大端，4 字节）：uint16 type + uint16 size
  type: 0 = Rest_In (cam→host)，2 = Rest_Out (host→cam)
  ⚠️ 注意语义与直觉相反：0 是"进（相机上报）"，2 是"出（主机下发）"

SslDataMsgHeader（大端）：int32 size + bytes
ThreeValueMsg（大端）：uint16 a + int32 b + int32 c
ProtocolMsgHeader（大端）：int32 numProtocols
ProtocolMsgProto（大端）：char[4] name + int16 id
  协议表硬编码：[('TCPT', 0x01), ('REST', 0x100)]
```

**⚠️ 陷阱**：
- **同一条消息里混用大小端**：`MsgHeader`/`CommonMsgHeader` 是大端，`InfoMsgHeader`（4.2）是小端。
- `size` 字段是从**本头起始**算起的总长，不是 body 长度。
- `Common_Hello` 的 body 是**变长协议表**（count + N×(4B name + 2B id)），必须循环解析。

### 4.4 TLS 隧道、证书与栈选型 ★★★（全项目最容易翻车的一处）

**数据流（PC 侧视角）**：

```
相机 TLS 输出字节 → USB 0x503 消息 → PC 的 TLS 服务端状态机 → 产出响应字节
                                                              ↓
相机 ← USB 0x503 消息 ← PC 的 TLS 服务端状态机 ← 相机发来的应用层字节
```

**必须实现的语义**：
- 服务端角色，**必须容忍客户端不发 SNI**（相机连的是 IP 语义，多半没有 SNI 扩展）。
- 需容忍**老密码套件**与**极低的 TLS 版本**（原项目曾显式锁定 `ssl.PROTOCOL_TLSv1`，即 **TLS 1.0**）。
- 支持**多连接**（相机可能重开隧道）。

#### 4.4.1 证书：**不能自签**，必须原样继承

原项目 `docs/AppInstallation.md:26` 的权威描述（原文）：

> "The network data is transmitted via USB. However, everything is SSL encrypted directly in camera. **Only https connections signed by a known root CA are allowed.** However, the certificate is still accepted if it is **expired, revoked and for a different host**."

同文档 `:30` 总结："**No origin verification** is performed in the whole process."

| 校验项 | 相机是否校验 | 依据 |
|---|---|---|
| 证书链签名（能否链到内置受信根 CA） | ✅ **必须通过** | 文档 :26 |
| 有效期 | ❌ 不校验 | 捆绑证书 2013 年即过期仍可用 |
| 吊销状态（CRL/OCSP） | ❌ 不校验 | 同上 |
| 主机名匹配 | ❌ 不校验 | 证书是 `*.localtest.me`，商店是 `playmemoriescameraapps.com` |
| 必须走 https | ✅ 必须 | 文档 :26 |

> ⚠️ 这一节推翻了本设计文档早期版本里"相机零校验、可用自签证书"的初判。**结论：证书与私钥是必须逐字节继承的资产，`rcgen` 之类的证书生成库在本项目里没有用武之地。**

**三条硬约束**：

1. **必须捆绑并使用 `certs/localtest.me.pem`**（叶证书 + 中间 CA + RSA-2048 私钥，结构见 §2.5）。
2. **TLS 服务端必须提供完整链（叶 + 中间 CA）**，否则相机无法链到 COMODO 根 → 握手失败。捆绑 PEM 里**只有叶 + 中间，没有根**（正确做法，根本应在对端信任库）。
3. **必须支持 SHA-1 签名与 TLS 1.0**（叶与中间证书都是 `sha1RSA`）。

#### 4.4.2 栈选型：rustls 大概率不行

从原项目的 git 历史可以还原出一段关键踩坑史（提交 `a1c6a67f` → issue #129 → 提交 `9ab9dbe0`）：

1. 最初用 Python 标准库 `ssl`，并**显式锁定 `ssl.PROTOCOL_TLSv1`**——说明相机客户端**只能谈到 TLS 1.0**，现代默认配置谈不下来（症状：`Communication error 201: Error completed (SSL error)`）。
2. 后来在 OpenSSL ≥ 1.1.1 上，加载这张 **SHA-1 签名的中间证书**时直接报 `CA_MD_TOO_WEAK`，握手失败。
3. 作者最终**把整个 TLS 栈换成纯 Python 的 `tlslite-ng`**（`requirements.txt:11`），因为它默认覆盖 TLS 1.0/1.1/1.2、不设弱摘要限制、且支持静态 RSA 密钥交换。

**rustls 已知不满足的地方**：只支持 TLS 1.2/1.3；**完全不支持静态 RSA 密钥交换**（`TLS_RSA_WITH_*`）；默认拒绝 SHA-1 签名方案。

**三条可行路线**：

| 方案 | 做法 | 前提 | 评价 |
|---|---|---|---|
| **① `openssl` crate（推荐）** | `set_min_proto_version(TLS1)` + `set_cipher_list("ALL:@SECLEVEL=0")`，复刻 tlslite-ng 的宽松策略；开 `vendored` feature 静态编译 | 接受编译时间与体积增加（部署仍是无 DLL 单文件） | **唯一能确定性复刻原版行为的方案**，因为原版最终就是这么活的 |
| ② rustls + 放宽配置 | 关掉 SNI 强制（`require_sni: false`），显式放开 `ECDHE_RSA` 套件与 SHA-1 签名 | **必须先确认相机 ClientHello 里有 ECDHE 套件**（阶段 0 的 E1 实验） | 若 E1 证实支持 ECDHE，这是更轻的选择（纯 Rust、无 C 依赖） |
| ③ 自写最小 TLS 服务端 | 固定 `TLS_RSA_WITH_AES_128_CBC_SHA`，只做一次 RSA 解密 + 记录层加解密 | 无外部库 | 约 300–500 行；因为只有一个已知客户端、无客户端证书、无扩展协商需求，复杂度可控，但要自己扛 CBC padding/MAC 的正确性 |

**决策方式**：先做 E1（抓 ClientHello 原始字节）。若里面有 `0xC013/0xC014`（ECDHE_RSA）就试 ②，否则直接上 ①。**不要在这件事上省那半天实验时间**——选错方向的代价是重写整个 TLS 层。

#### 4.4.3 必须先做的实验（阶段 0 的验收标准）

> 把相机在 `Tcp_ProxyConnect` 之后发来的**第一个 `0x503` 消息的原始字节 dump 成 hex**，然后解析：
> 1. `legacy_version`（ClientHello 里是 `0x0301` = TLS1.0 还是 `0x0303` = TLS1.2）；
> 2. `cipher_suites` 列表（重点找 `0x002f` = TLS_RSA_WITH_AES_128_CBC_SHA、`0x0035`、`0xc013/0xc014` = ECDHE_RSA）；
> 3. 是否有 `server_name(0)` 扩展，`signature_algorithms` 里有没有 RSA/SHA1。

### 4.5 HTTP 服务端的真实语义（不是"HTTPS 服务器"，而是一个 fallback handler）★★

`HttpHandler`（`marketserver/server.py:11`）**只有两个方法，完全不看 Host / 路径 / UA / Cookie / Authorization**：

| 方法 | 匹配规则 | 状态行 | Content-Type | 其它头 | Body |
|---|---|---|---|---|---|
| `POST` | **任意 host/任意路径** | `HTTP/1.0 200 OK` | `application/vnd.sony.spk.package-archive`（⚠️ 不是 `application/json`） | `Connection: Keep-Alive`、`Content-Length` | 动作 JSON |
| `GET` | **任意 host/任意路径** | `HTTP/1.0 200 OK` | 同上（SPK MIME） | `Connection: Keep-Alive`、`Content-Length`、`Content-Disposition: attachment;filename="app.1.spk"` | 整个 SPK |
| 其它 | — | `501`（CPython 默认） | | | |

**七个必须复刻或注意的行为细节**：

1. **状态行是 `HTTP/1.0`**（`protocol_version` 未覆盖），但响应里硬编码了 `Connection: Keep-Alive`（`server.py:20`）。CPython 在 HTTP/1.0 下仍会置 `close_connection=True` → **实际每个请求后就关连接，`Keep-Alive` 只是给相机看的**。→ Rust 实现**不需要真正的 keep-alive**，按请求-响应-关闭即可（这也解释了为什么"POST 下令 → GET 下载"两个请求仍能工作：相机自己重开了连接）。
2. **相机发来的 POST 必须带 `Content-Length`**：`int(self.headers['Content-Length'])`（`server.py:29`）没有兜底，缺失会抛 `KeyError` → 连接中断。Rust 侧应容忍缺失（更健壮），但要清楚相机实际一定会带。
3. **响应永远带精确 `Content-Length`，绝不 chunked**；**没有 `Range`/`206`/`ETag` → 不支持断点续传**，中断只能整包重下。
4. **转发粒度是 16 KiB**（`installer/__init__.py:67` 的 `sock.recv(2**14)`）——这是 USB 侧 TLS 隧道的搬运粒度，**与 HTTP chunked 无关**。UI 进度条基于这个粒度累加即可。
5. **端口可以随便选**：`self.url = 'https://' + host + '/'`（`server.py:46`）**不含端口号**，真实端口只经 `installer.install(..., *server.server_address, ...)`（`commands/usb.py:73`）用于本地连接。→ **Rust 侧绑 `127.0.0.1:0` 让系统挑端口完全可行**，彻底消除端口冲突。
6. **原实现的三个健壮性缺陷，Rust 应修掉**：APK 未设置时 GET 会 `spk.dump(None)` 抛 `TypeError` → 连接被重置（应为 404）；`BaseHTTPRequestHandler.timeout` 未设置 + 单线程串行 → 一个卡住的连接会阻塞后续所有连接（应设超时）；`self.result` 一旦写入永不回退（重试 POST 只会拿到空 actions，相机可能直接放弃）→ 建议按 `session.correlationid` 去重并允许重复派发。
7. **两个 URL 的分工不要混淆**（`server.py:46` 与 `marketserver/constants.py:3`）：

   | 位置 | 值 | 说明 |
   |---|---|---|
   | XPD 的 `TCD` | `https://www.playmemoriescameraapps.com/`（**真索尼域名**） | 故意伪装。原项目提交 `f0ceb822` 的标题就是 *"Fake url in xpd when using local server #33"*——**必须让相机看到正规域名它才肯继续** |
   | 商店 JSON 的 `actions[0].args` | `https://127.0.0.1/`（`server.py:46` 的 `self.url`） | 相机据此发起第二次请求下载 SPK |

> 📌 **对你原始需求的一处修正**：你提到"HTTPS 服务器用 axum 或 hyper"。基于以上分析，**这里并不需要一个 HTTP 服务器框架**——它的路由逻辑等价于 `match method { GET => spk, POST => json }`，没有路径、没有中间件、没有并发需求，还要跑在一条由 USB 报文驱动的自定义字节管道之上（而不是 TCP accept 循环），且必须手写 `HTTP/1.0` 状态行与精确头部。引入 axum/hyper 会带来"把内存状态机伪装成 IO stream"的额外适配成本，收益接近零。**建议本期手写约 80 行的响应构造器**，hyper 留作将来改走真 socket 时的备选（见 §11 D5）。

### 4.6 REST/HTTP 语义与 JSON 载荷 ★

**主机 → 相机（唯一的启动请求，`installer/__init__.py:17-18`）**：

```
POST /task/start REST/1.0\r\n
Content-type: application/x-psn-dstartup2\r\n
\r\n
<XPD 内容>
```
⚠️ 只有 `Content-type` 一个头（注意头名是**小写 t**），只有 `\r\n\r\n` 一个分隔；HTTP 版本串是自定义的 `REST/1.0`；**没有 `Content-Length`**（长度由 USB 侧 `RestMsgHeader.size` 给出）。

**相机 → 主机（两类）**：

```
POST /task/progress REST/1.0  body: {"status":n,"status text":"...","percent":p,"total size":t}
POST /task/complete REST/1.0  body: {"resultCode":c,"message":"..."}
```
字段名里有**空格**（`"status text"`、`"total size"`）——照抄，Rust 侧用 `#[serde(rename = "status text")]`。

**相机上报的完整 JSON 结构**（`marketserver/__init__.py:8-39`，可直接作为 serde 定义）：

```jsonc
{
  "accountinfo":  { "signinid": "...", "accountid": "...", "registered": "1" },
  "applications": [ { "name": "...", "version": "..." } ],       // 已安装应用
  "deviceinfo":   { "deviceid": "...", "fwversion": "...", "productcode": "...",
                    "name": "...", "battery": "...", "freespace": "...",
                    "storagetotalsize": "..." },
  "session":      { "correlationid": "..." },
  "profileversion": { "version": "1" }
}
```

⚠️ **这些字段全部以字符串形式传输**（连 `registered`/`version` 都是 `"1"` 这样的字符串），serde 不要写成数字类型，否则解析失败。

💡 **一个原项目没做的增强**：`deviceinfo.name`/`productcode`/`fwversion`/`freespace` 可以直接用来**丰富 UI 的设备信息卡**（比额外发命令更省事），`freespace` 还能在安装前**预检空间是否够装**，对用户很有价值。

**主机 → 相机的商店响应（JSON）**：

```json
// 第 1 次 POST：下令安装
{"actions":[{"command":"dlandinstall","args":"https://127.0.0.1/",
             "attrs":[{"attrname":"appname","attrvalue":"app"}]}]}
// 之后所有 POST：空动作 = 结束
{"actions":[]}
```
`args` 是 SPK 的完整 URL；`appname` 是给相机 UI 显示的名字（原实现固定 `'app'`，新项目可考虑填应用名，**但要注意非 ASCII 字符能否被相机接受，建议保守只用 ASCII**，见 §11 D3）。

### 4.7 SPK 容器格式 ★

```
magic '1spk' (4B) | keyOffset uint32 LE (=0) | keySize uint32 LE (=256)
| encryptedKey(256B, 固定常量) | encryptedData(AES-128-ECB，1 MiB 分块，每块 PKCS#7)
```
- **AES 密钥硬编码**：`c301afd22ddba4c090eca46258e4bfb1`（Python 独立复算 + 与 Rust 输出逐字节比对验证，见 §2.6）→ **Rust 侧不需要任何 RSA 实现**
- `blockSize = 0x100000`（1 MiB）、`paddingSize = 16`、密文块 = **`0x100010`**
- 文件名后缀 `app.1.spk`；MIME `application/vnd.sony.spk.package-archive`
- 校验：`isSpk()` 只检查 magic
- 安全提示：**SPK 无签名、无 MAC，任何人都能构造**——这不是漏洞，而是原方案能成立的前提

### 4.8 XPD 文件 ★

```ini
[DrmTCD]
TCD = https://www.playmemoriescameraapps.com/
TKN = 0
CIC = <hex>
```
- 生成时用 Python `ConfigParser.write()` 的默认格式：`[节]` + 每行 `键 = 值`（**键与值之间是 ` = `**），**行尾 `\n`**（不是 CRLF），末尾**多一个空行**（`write()` 会补）。⚠️ 这种"格式细节靠库实现"的地方，Rust 必须**手工精确拼字符串**并写单元测试比对原文件字节。
- `CIC = HMAC-SHA256(key=cicKey, msg=TCD.encode('latin1')).hexdigest()`（**小写 hex**）
- `cicKey`（**45 字节**，`xpd/constants.py:5`，90 个十六进制字符，逆向自索尼 APK）：
  ```
  hex: 8595e68aa50d25dcc52b4d6e6a62af526efd7523a4cc47e212e82e979728d6f0dd02c7e4e79ddb317d56fea2bd
  ```
- MIME：`application/x-psn-dstartup2`
- 真商店下发的 XPD 还可能含 `FNAME`/`OUS`（文件名 / SPK URL），我们的假商店不需要这两个键

### 4.9 APK 元数据解析 ☆

需要从 APK 里取：`package`、`versionCode`、`versionName`、`minSdkVersion`、签名证书（主机侧**不校验签名**，仅做展示/兼容性提示）。
- 原实现：`axmlparserpy`（AXML 二进制 XML 解析）+ `asn1crypto`（证书）。
- Rust 侧：可用现成的 AXML crate，**或**直接实现最小 AXML 解析（只需 4 个属性；`versionCode`/`minSdkVersion` 是 **attribute 而不是元素文本**，注意别写成读文本）。轻量自实现反而更可控，避免引入大依赖。
- **校验策略（新项目升级点）**：`minSdkVersion > 10` 时在 UI 上给出明确警告条（相机为 Android 2.3.7，API 10），并允许用户"我坚持要装"。

### 4.10 服务模式 senser 认证（本期不实现，但记录）⚠️

- `usb/crypto.py` 是手写 SHA-1，其中 `sha1_faulty(message) = sha1(message, len(message) & 0x1f)` 复刻了索尼 senser 组件的**长度计算 bug**。
- 认证流程 `SonySenserAuthDevice.authenticate()`（`usb/sony.py:918-936`）迭代 **3 轮**，密钥表 `senserKeysSha1`/`senserKeysSha256` 硬编码在 `usb/constants.py`；仅 `idProduct == 0x0336` 时拼接额外 key。
- **⚠️ 用标准 `sha1` crate 会认证失败**：必须自己按"长度字段被 `& 0x1f` 污染"的语义重算摘要。这是本期不做服务模式的技术理由之一。

### 4.11 状态机与错误分类 ☆

原实现几乎用裸 `Exception`。新项目应定义结构化错误，并且**区分"可重试"和"需用户操作"**：

| 场景 | 类别 | UI 行为 |
|---|---|---|
| 没找到设备 | 用户操作 | 「请用 USB 连接相机并切到 MTP 模式」+ 重试按钮 |
| 找到多台 | 用户操作 | 「检测到多台设备，请只保留一台」 |
| 相机不支持 App（`InvalidCommandException`） | 不可恢复 | 「此机型不支持应用安装」+ 兼容列表链接 |
| 模式切换后 5 秒没出现安装模式设备 | 可重试 | 倒计时 + 「在相机上确认后重试」 |
| PTP 忙码超时 | 可重试 | 「相机忙，正在重试（第 n 次）」 |
| XPD `resultCode != 0` | 不可恢复 | 显示相机原始 message |
| TLS 握手失败 | 不可恢复（需上报日志） | 「与相机协商失败」+ 导出诊断日志按钮 |
| 相机空间不足（`freespace` 预检） | 用户操作 | 「相机剩余空间不足，需要 X MB」 |
| 用户在传输中断开 USB | 可重试 | 「连接中断，请重新插拔」 |

## 5. Rust 项目模块划分建议

### 5.1 总体原则

三条铁律：

1. **`core` 不许依赖 `iced`**。业务逻辑必须能脱离 GUI 运行（否则无法写集成测试，也无法复用到 CLI/将来可能的移动端）。
2. **UI 与后端只通过"消息 + 事件"单向流动通信**。UI 发命令，后端发事件，中间不共享可变状态。
3. **平台差异收敛在 `driver` trait 之后**。上层协议栈完全不感知自己跑在 WPD 还是 WinUSB 上。

```
└───────────────────────────────────────────────────────────────┘
```

**关键设计决策：把"本地 HTTPS 服务器"从 TCP socket 降级为内存状态机。**

原实现先起一个真的 `TCPServer`，再让主循环把 USB 字节灌进出。这带来三个问题：端口占用、防火墙弹窗风险、多一次内核拷贝。新实现里 **`TlsEngine` 就是一个 `feed(bytes) -> Vec<bytes>` 的状态机**，USB 字节直接喂进去，输出的字节直接回灌 USB。好处：

- 不占端口、不需要 `tokio::net`、不触发防火墙；
- 可单测（喂一段录制的 ClientHello hex，断言输出的 ServerHello）；
- 多连接天然支持（`HashMap<conn_id, TlsEngine>`）。

### 5.5 UI ↔ Core 的接口契约（伪代码，用于对齐认知）

```rust
// ── UI → Core ────────────────────────────────────────────────
pub enum UiCommand {
    Rescan,                                  // 重新扫描设备
    InstallFromFile(PathBuf),                // 从本地 APK 安装
    InstallFromPackage(String),              // 按包名（从列表）安装
    Cancel,                                  // 取消当前任务
    Shutdown,
}

// ── Core → UI ────────────────────────────────────────────────
pub enum BackendEvent {
    Devices(Vec<DeviceInfo>),                // 设备列表变化（热插拔）
    JobState(JobState),                      // 状态机迁移（驱动 UI 文案与按钮可用性）
    Progress { stage: Stage, percent: f32, detail: String },
    Log(LogLine),                            // 「显示日志」抽屉
    Finished(Result<InstallReport, InstallError>),
}

pub enum JobState {                           // 直接映射 §3.0 的 P0..P10
    Idle, Preparing, Connecting, SwitchingMode { attempt: u8, deadline: Instant },
    WaitingReconnect { elapsed: Duration }, Handshaking, SendingTask,
    Downloading { received: u64, total: u64 }, Installing, Done,
}

pub struct InstallError {                     // §4.11 的错误分级
    pub kind: ErrorKind,
    pub retryable: bool,
    pub hint_zh: &'static str,                // 直接可显示的中文排查建议
    pub source_chain: Vec<String>,            // 导出诊断用
}
```

**为什么这样切分很关键**：`JobState` 是 UI 的**唯一真相**。UI 不需要知道 USB、TLS、SPK 的存在，只需要把 `JobState` 渲染成中文文案 + 进度条。这直接消灭了原项目里 `PrintRedirector` 把 stdout 重定向到 tkinter 文本框那种耦合（`pmca-gui.py:19-31`）。

### 6.4 中文字体方案（必须显式处理）

Iced 默认字体是 Fira Sans，**不含 CJK 字形**，中文会显示成方框（豆腐块）。方案：

1. **首选：加载系统字体**（Windows 上 `C:\Windows\Fonts\msyh.ttc` 微软雅黑）。用 Iced 0.14 的字体加载 API 在启动时把字节交给渲染器，然后在主题里全局指定 `font`。
2. **兜底：内嵌一个精简子集字体**（如思源黑体子集 / Noto Sans SC Subset），只保留常用汉字 + 拉丁，约 1–3 MB。
3. 字体回退链：`微软雅黑 UI → 微软雅黑 → Noto Sans SC Subset`；数字/版本号用等宽（`Consolas`/内嵌等宽）避免错位。
4. ⚠️ 字号必须随 DPI 缩放（Iced 默认按 scale factor 处理，但**自绘 Canvas 里的文字要手动乘 `scale_factor`**，否则 125%/150% 下糊）。
5. ⚠️ 中文换行不能按空格断词：较长的错误提示要允许**逐字换行**（Iced 的 `text` 默认按词断行，中文长串可能撑破卡片）。必要时手动插 `\u{200B}`（零宽空格）或在文案里预留换行。

## 7. 中文路径问题：排查点与解决方案

### 7.0 先给结论（避免做无用功）

**核心事实：安装主链路根本不接触 PC 文件系统路径。**

相机是通过 USB 报文拿数据的，它永远看不到 `D:\我的照片\相机\应用.apk` 这种路径。原项目里能用中文路径跑通安装，正是因为这条链路上没有路径参与。

所以中文路径的风险**只存在于 4 个本地环节**：① 选/读 APK 文件；② 下载缓存目录；③ 配置与日志目录；④ 对外部进程的调用。

**第二个核心事实：Rust 在 Windows 上是"默认正确"的。**

| 环节 | Python 的行为 | Rust 的行为 |
|---|---|---|
| 表示路径 | `str`（UTF-8）→ `os.fsencode` 按 `locale` 转 → Windows ANSI 代码页，**中文系统上是 GBK，非中文系统上是 CP1252 → 直接崩** | `PathBuf` 底层是 `OsString`（Windows 上即 UTF-16）→ 直接调用 `CreateFileW` 等宽字符 API |
| 打开文件 | 依赖 `sys.getfilesystemencoding()` + `surrogateescape` 兜底 | `std::fs::File::open` 走宽字符 API，天然支持 |
| 子进程参数 | `subprocess` 在 Windows 上传 `lpCommandLine`，Python 3 会正确处理，但**拼接字符串 + `shell=True` 时按 ANSI 处理会乱码** | `std::process::Command` 用 `CreateProcessW`（宽字符），参数为 `OsStr`，天然支持 |

> 补充一个客观事实：原项目在 Python 侧的本地路径处理其实**没有**显式编码问题（全仓库 grep `fsencode`/`getfilesystemencoding`/`surrogateescape`/`locale.` **零命中**），它靠的是 Python 3 的隐式宽字符机制；**真正会崩的是相机协议里那些硬编码的 `latin-1`/`ascii` 编解码**（例如把中文 SSID 或中文推文文案发给相机时会 `UnicodeEncodeError`）——而这类路径我们本期根本不走。

**结论：Rust 把这个问题的性质从"到处踩坑"降级为"只要不主动犯 5 类错误就没事"。**

### 7.1 排查点清单（按风险从高到低）

| # | 排查点 | 风险 | Rust 对策 | 验证方法 |
|---|---|---|---|---|
| C1 | **`Path → &str` 的强制转换** | ⚠️ **最高危**：`path.to_str().unwrap()` 遇到非法 UTF-16（未配对代理项）返回 `None` 并 panic | **全项目禁止 `to_str().unwrap()`**；用 `Path::display()` 打日志、用 `PathBuf` 传递、必须转字符串时用 `to_string_lossy()` 且**仅用于显示** | 单测：构造含 emoji / 未配对代理项的路径 |
| C2 | **外部进程调用** | 命令行注入 + ANSI 编码风险 | 用 `std::process::Command`（宽字符）；**禁止 `cmd /c` 拼接字符串**；必须用 PowerShell 时用 `-File` + 参数数组而非 `-Command` 拼串 | 集成测试：在中文目录下启动一个回显参数的子进程 |
| C3 | **C 库边界** | libusb/OpenSSL 等 C 库若收 `char*` 路径会退化为 ANSI | 设备路径是系统生成的 ASCII（`\\?\usb#vid_054c&pid_...`），风险低；**要盯的是日志/证书/固件文件路径** | 全仓 grep `CString`/`CStr`/`as_ptr`，逐处确认来源 |
| C4 | **临时目录** | `%TEMP%` 通常含中文用户名（`C:\Users\张三\AppData\Local\Temp`） | 用 `std::env::temp_dir()`（宽字符正确）或 `directories::ProjectDirs`；**不要自己拼 `C:\Users\...`** | 在中文用户名机器上跑一遍 |
| C5 | **MAX_PATH 260 限制** | 中文路径 + 长文件名 + 深层目录极易超 260 | Rust std 的 `std::fs` 对绝对路径会自动加 `\\?\` 前缀，但仍受限于进程清单的 `longPathAware`；对策：**入口处检测路径长度，超限时提示或自动复制到短临时路径**；`app.manifest` 声明 `longPathAware=true` | 测试：25 层中文目录 + 长文件名 |
| C6 | **日志文件编码** | Python 3 默认按 locale 写日志（中文 Windows 是 GBK），跨机器打开乱码 | 统一 **UTF-8**（可加 BOM 便于记事本识别），用 `tracing` 的 writer 确保不丢字符 | 用 VS Code + 记事本分别打开日志 |
| C7 | **配置/缓存目录** | `os.path.expanduser('~')`，中文用户名 | `directories::ProjectDirs::from(...)` 返回 `PathBuf`；**不要手动拼盘符**；配置文件用 UTF-8 | 中文用户名下检查目录创建 |
| C8 | **文件选择框** | tkinter `filedialog` 返回 str | `rfd::FileDialog` 返回 `PathBuf`，正确；⚠️ **别把返回值立刻转成 `String` 存进 UI 状态**，否则 C1 复现 | 选一个中文名 APK |
| C9 | **`Content-Disposition` 文件名 / JSON 里的应用名** | 原项目固定 ASCII `'app'` | 保持 ASCII；相机端是 Android 2.3 + 自研下载器，**非 ASCII 文件名行为未验证** | 若确实要用中文名，先在阶段 0 试（§11 D3） |
| C10 | **构建期路径** | PyInstaller 用 `sys._MEIPASS` 解压到临时目录（含中文用户名 → 曾有大量失败案例） | 用 `include_bytes!` 把证书等资源编进二进制，**运行时不需要任何外部资源路径**；⚠️ 工作区路径建议保持 ASCII（MSVC 偶发异常） | CI 上用一个中文路径的构建目录跑一次 |
| C11 | **崩溃转储/诊断包** | — | 文件名用时间戳而非设备名；打包 zip 时显式设置 UTF-8 文件名标志位（flag bit 11） | 导出一次诊断包并解压 |

### 7.2 关于"子进程调用"的具体规则

即便本期功能**不需要调用任何外部程序**（不装驱动、不调 adb、不调 pnputil ——原项目同样"运行时零外部进程、零注册表写入、零提权"），也先把规则定下来，因为将来很可能要加"打开日志目录"之类的功能：

```rust
// ✅ 正确
Command::new("explorer.exe").arg(format!("/select,{}", path.display())).spawn()?;
// ⚠️ explorer 的 /select, 参数对含空格/逗号/中文的路径敏感：
//    必须不加引号地传完整路径（Windows 的怪癖），且路径不能含英文逗号——含逗号时降级为直接打开父目录

// ✅ 更稳的替代：直接用 ShellExecuteW（windows crate）打开目录，不经过命令行解析
//    ShellExecuteW(None, "open", dir, None, None, SW_SHOWNORMAL)

// ❌ 禁止
Command::new("cmd").args(["/c", &format!("copy \"{}\" ...", p)])   // 命令行解析 + ANSI 风险
Command::new("powershell").arg(format!("-Command Copy-Item '{}'", p)) // 引号注入 + 编码风险
```

**四条硬规则**：
1. `Command` 的每个参数走 `.arg()`，**永不拼字符串**；优先无 shell 调用。
2. 传给外部进程的路径优先用 `OsStr`/`Path`，**不要先转 `String`**。
3. 若必须用 PowerShell，用 `-File script.ps1 -Arg <path>`（参数以 UTF-16 传递），并显式 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`。
4. 任何外部进程调用都要有**超时 + 杀进程 + 捕获 stdout/stderr 并按 UTF-8 解码**（`String::from_utf8_lossy`）。

### 7.3 两个容易被忽略的点

- **"伪中文路径问题"**：`switchToAppInstaller()` 之后相机重启，重新枚举会用到**设备路径字符串**（如 `\\?\usb#vid_054c&pid_...`）。这些是**系统生成的纯 ASCII**，与用户名/安装目录无关，**不构成中文路径风险，别在这里浪费时间**。
- **相机侧路径不是 PC 路径**：相机内部是 POSIX 路径且**大小写敏感**（`/setting/updater/dat4`、`{dataDir}/system/packages.xml` 等）。将来若做扩展功能，**不要用 `std::path` 处理相机侧路径**，应引入独立的 `CameraPath` 类型（同时拒绝 >0xFF 的字符，因为协议里用 `latin-1` + 4 字节 NUL 对齐）。

## 8. 性能优化方案

### 8.1 目标（可验收）

| 指标 | 目标 | 测量方法 |
|---|---|---|
| 冷启动到可交互 | **≤ 300 ms** | 从进程创建到首帧呈现（`Instant` 打点 + 事件循环首帧） |
| 空闲 CPU | **≈ 0%**（单核 < 0.5%） | 任务管理器观察 60 秒 |
| 空闲内存 | ≤ 120 MB（GPU/纹理占大头） | 任务管理器 |
| 20 MB APK 安装总耗时 | 不慢于原 Python 实现（≤ 60 s 量级） | 计时日志 |
| 单文件发布体积 | ≤ 12 MB（不含字体子集） | Release exe 大小 |
| 安装期间 UI 帧率 | ≥ 60 fps，无掉帧 | 拖动窗口观察 |

### 8.2 启动优化（按收益排序）

1. **`include_bytes!` 内嵌资源**：证书、图标、默认配置全部编进二进制。原项目用 `sys._MEIPASS` 解压到临时目录，这既是启动瓶颈也是中文路径事故源。**这是最大的一项收益。**
2. **`#![windows_subsystem = "windows"]`**：避免弹出控制台窗口（也避免控制台初始化开销）。
3. **延迟初始化**：不要启动时就枚举 USB、不要启动时加载应用列表。首帧只渲染静态骨架，USB 扫描放到首次 `Subscription` 里。
4. **renderer 选择**：默认 `wgpu`；对老显卡/虚拟机提供 `tiny-skia`（软件渲染）回退开关（设置页可切，或启动参数 `--software-render`），避免"打开就黑屏"。
5. **release profile**：
   ```toml
   [profile.release]
   opt-level = 3
   lto = "thin"          # 实测比 fat 编译快很多、体积接近
   codegen-units = 1
   panic = "abort"       # 体积与性能双收益（注意：会失去 unwind 型恢复，需先确认无依赖 unwind 的逻辑）
   strip = "symbols"
   ```
6. **避免首帧字体加载阻塞**：系统字体加载 + 度量是启动期较重的操作，若明显 >50 ms，改为"先用兜底字体渲染首帧，字体就绪后重绘一次"。
7. ⚠️ **首次运行会被 Defender 扫描**，这个延迟无法从代码消除（代码签名 + 用户加白名单是唯一解）。

### 8.3 异步 / 线程模型（明确到线程数）

```
线程 0  main            Iced 事件循环 + 渲染（订阅 tokio feature 作为 executor）
线程 1..N tokio runtime 协调层：State 迁移、事件派发、TLS 状态机
线程 X  "usb" 专用线程   所有 USB I/O（阻塞式读，1 个线程足够）
线程 Y  "worker"         文件读取 / SPK 打包 / SHA 计算（磁盘与 CPU 密集）
```

**规则**：
- USB 有且**只有**一个线程持有设备句柄，且**不持有任何锁**——所有跨线程通信走 `async_channel`（有界，容量 256）。这样从根本上消除死锁与"UI 阻塞在 USB 读上"。
- USB 线程用**阻塞读 + 事件驱动**，不用忙等（原项目 `while True: receive(); if None: continue` 会烧掉一个核）。
- 需要重试的忙码（`0xA489`）用**指数退避 1ms→2ms→…→200ms + 5 秒总超时**，并向 UI 上报"重试中"。
- 文件/加密工作用 `tokio::task::spawn_blocking`，不占协调线程。
- **进度事件限流**：USB 每次搬运都发事件会淹没 UI 通道。策略：**最多每 100 ms 或每提升 1% 发一次**（合并丢弃中间值）。
- 取消：`CancellationToken`（`tokio-util`）贯穿各阶段；USB 线程在两次读之间检查取消标志。

### 8.4 内存与大文件处理

- **APK/SPK 全程驻内存**（典型 5–40 MB，峰值 < 100 MB），**不落盘**：既省一次磁盘往返，又彻底消除中文临时路径问题。
- AES 分块加密 **原地（in-place）复用缓冲**：避免 1 MiB × N 的临时分配。
- 发送时把 SPK 切成 16 KiB 的 `Bytes`（引用计数切片）交给 USB 线程，**零拷贝**（`bytes::Bytes`）。
- 进度百分比用 `u64` 计算，不做整数除法丢精度。

### 8.5 UI 层性能

- **不要订阅 `window::frames()`**：那会强制每帧重绘。只在数据变化时更新状态 → Iced 自动按需重绘。
- 长列表（应用库）用 `lazy` feature 做虚拟化；`scrollable` 里避免每项都建复杂子树。
- 日志抽屉**上限 2000 行环形缓冲**，超出丢弃最旧的；渲染时只 build 可见区域。
- 动画（呼吸点）用 8–15 fps 的 `Subscription`，而不是 60 fps。
- 所有文案常量用 `&'static str`，避免每帧 `format!` 分配；进度百分比等少数动态文本再格式化。

### 8.6 网络与缓存（应用库）

- 应用列表首次拉取后缓存到 `%LOCALAPPDATA%\<app>\cache\apps.json`，**TTL 24 小时**；启动时先用缓存渲染，后台静默刷新。
- 下载的 APK 也做缓存（按 URL 的 SHA-256 命名），重复安装无需重新下载。
- GitHub API 有速率限制：**必须处理 403 + `X-RateLimit-Reset`**（匿名 60 次/小时/IP），并给用户可读提示（"列表刷新过于频繁，请 N 分钟后重试"）。

## 9. 分阶段实现计划

原则：**先把不确定性打掉，再写代码；每一步都有可独立验证的产出，不做"写完全部再联调"。**

### 阶段 0：风险实验（0.5–1 天，**不写产品代码**）

目标：把 §4.4 里"可能推翻技术选型"的未知数变成已知数。产出是一份实验记录 + 几段 hex 样本。

| 实验 | 做法 | 判定 |
|---|---|---|
| **E1 抓 ClientHello** | 用原 Python 项目跑一次安装，在 `installer/__init__.py` 的 `SslStartMessage` 分支后把收到的 `0x503` 原始字节 dump 成 hex（或在 `sock.connect` 之前把 TLS 首包写文件） | 得到 `legacy_version`、`cipher_suites`、有无 `server_name(0)`、`signature_algorithms` 内容 |
| **E2 试 http 旁路** | 把 `marketserver/constants.py:3` 的 `baseUrl` 与 `server.py:46` 的 `self.url` 临时改成 `http://…`，跑一次 | 相机是否仍发起 `TcpProxyConnect`（若不再发起 → 支持明文 http → 最高风险项直接消失） |
| **E3 证书最小集验证** | 从捆绑 PEM 里只留叶证书（去掉中间 CA）跑一次 | 若失败 → 证实"必须提供完整链"，把这条写进实现约束 |
| **E4 录样本** | 录制三段黄金样本：`Common_Hello` 完整字节、一次 `/task/start` 的响应、一个真实 APK 的 SPK 输出 | 作为后续单元测试的期望值 |

**阶段 0 交付**：`docs/experiments.md`，含 4 个实验结论 + hex 样本 + TLS 选型决定（openssl / rustls / 手写 / http 旁路）。

**为什么不跳过它**：E1 的结论直接决定 `sony-core/src/tls/` 是"200 行胶水"还是"500 行手写 TLS"。两者的排期差 2–3 天。花半天换取这个确定性，是整个计划里性价比最高的一步。

### 阶段 1：USB 打通（2–3 天）

**范围**：能枚举出索尼相机、能读出 DeviceInfo、能正确分类模式。**没有 UI、没有协议栈、没有安装。**

- 建 workspace 骨架（`sony-usb` / `sony-core` / `app` 三个 crate，`app` 先只打印）
- `sony-usb`：`trait Driver`、设备枚举、`GetDeviceInfo` 响应解析（Manufacturer / Model / VendorExtensionString / OperationsSupported）
- 先只做 `nusb` 一条后端（最快见效），后做 Windows 免驱后端
- 临时 CLI：`sony-probe list` / `sony-probe info`，输出中文表格

**验收**：插上相机，`sony-probe info` 能打印出与 `pmca-console.py info` 一致的机型/固件/序列号；普通 MTP、安装模式、MSC 三种状态都能被正确识别（安装模式可用原 Python 工具切过去）。

**风险点**：Windows 上相机被系统驱动占用 → 这时才会暴露 R2，正好在写 UI 之前决定驱动策略。

### 阶段 2：协议栈 + TLS（4–7 天，**最关键的一段**）

**范围**：能完整走通一次安装，**用命令行验证，先不做 UI**。

- `proto/ptp`：PTP 容器编解码 + 代理消息（`0x9488/9/C/D`）+ 忙重试 + `dataSize` 截断
- `proto/sony`：Common/TCP/REST 三种信封 + 协议表握手（`0x400/0x401/0x402`）
- `tls/`：按阶段 0 结论实现
- `store/xpd` + `store/market`：XPD 生成、JSON 响应
- `job/`：P0..P10 状态机骨架，事件通过 channel 输出（先打到 stdout）
- APK 的 SPK 先用**原 Python 工具预生成好的文件**，本阶段不做打包

**验收（DoD，逐条打勾）**：
1. 在普通 MTP 模式下能发出 `NotifyScalarDlmode (5,2)` 并让相机切模式；
2. 5 秒窗口内能重新枚举到安装模式设备；
3. `sendInit` 能收到 `Common_Hello` 并解析出 `TCPT`/`REST`；
4. `/task/start` 收到 `resultCode == 0`；
5. TLS 隧道建立后，相机能发出第一个 HTTPS 请求（日志可见 POST /）；
6. `dlandinstall` 下发后，相机开始 GET，且**传输完整**（用预生成的 SPK 验证）；
7. 收到 `/task/complete`，`sendEnd()` 后相机侧完成安装。

**风险点**：这是全项目唯一"可能卡住很久"的阶段。**卡住时的取证手段**：把每一层的原始字节都按方向 dump 到文件（`--dump-proto` 开关），再与 E4 样本逐字节比对。

### 阶段 3：SPK 打包 + APK 解析（1–2 天）

- `store/spk`：容器写入，**AES 密钥硬编码 `c301afd22ddba4c090eca46258e4bfb1`**，无需 RSA
- `apk/`：最小 AXML 解析（package / versionName / versionCode / minSdkVersion）
- 中文路径相关：全部走 `PathBuf`，落地 §7.1 的 C1/C4/C5 检查点

**验收**：
1. **逐字节比对**：同一个 APK，Python `spk.dump()` 与 Rust 实现的输出**完全一致**（含块大小 `0x100010`）；
2. 用 Rust 生成的 SPK 走完阶段 2 的流程，相机能装成功；
3. 中文路径 + 空格 + emoji 的 APK 文件名全流程不报错；
4. AXML 解析结果与 `aapt dump badging` 一致。

### 阶段 4：Iced 界面（5–8 天）

- 主题与 token（§6.0）、字体加载（§6.4）、主窗口骨架
- 4 个页面 + 组件库（§6.2/§6.3）
- 订阅 `BackendEvent` → 驱动 `JobState` → 渲染中文文案
- 模式切换的强提示态（这是体验分水岭）
- 日志抽屉、错误横幅（§4.11 的 `hint_zh`）

**验收**：一个没读过文档的人，插上相机后能**在 3 次点击内**完成安装；中途黑屏时会看懂提示；四种典型错误（无设备/多设备/不支持/超时）都有可操作的中文指引；中文界面无豆腐块；125%/150% DPI 下不糊。

### 阶段 5：打磨（3–5 天）

- 性能达标（§8.1 的 6 项指标）
- 诊断包导出（脱敏后的日志 + 环境信息）
- 内嵌应用列表 + 缓存（可选）
- 单文件发布、图标、版本信息、安装包制作
- 在至少 2 台真机 + 1 台虚拟机上回归

### 9.0 里程碑依赖图

```
阶段0(实验) ──┬─→ 阶段2(协议栈) ──┬─→ 阶段3(SPK) ──┐
              │                    │                ├─→ 阶段5(打磨)
阶段1(USB) ───┴────────────────────┴─→ 阶段4(UI) ───┘
                ↑ 可并行               ↑ 依赖阶段2的 JobState 接口
```

**并行建议**：阶段 0 与阶段 1 可并行（一个人跑实验，一个人搭 USB 层）。阶段 4 的 UI 骨架（主题/字体/静态页面）可在阶段 2 期间用假事件流并行开发——这正是 §5.5 把 `BackendEvent` 定成纯数据的价值所在。

### 10.1 无需相机的自动化测试（覆盖约 80% 的代码行）

| 测试层 | 手段 | 覆盖内容 |

## 11. 待你确认的决策点

### D1. Windows 驱动策略（影响最大，建议选 A）

| 方案 | 优点 | 缺点 | 工作量 |
|---|---|---|---|
| **A. 原生免驱后端（SCSI Pass-Through + WPD COM）** | 开箱即用，零外部工具，不动系统驱动（不影响相机日常使用） | 需要写 Windows 专属代码 | +2~3 天 |
| B. `nusb`（WinUSB） | 跨平台统一、代码量小 | 需要用户用 Zadig 换驱动；**换完之后相机可能无法被系统识图/传照片**，卸载麻烦 | 基线 |
| C. A + B 双后端 | 兼容性最好（A 优先，失败时提示改用 B） | 代码量最大 | +3~4 天 |

**我的建议：先按 A 做，把 B 作为"可随时启用的备用路径"。** 理由是这是给普通用户用的中文工具，"先装驱动"的体验与目标冲突。

### D2. 是否需要"明文 http 旁路"（阶段 0 的 E2）

如果 E2 成功，安装链路会变简单、更快，且不再依赖那张家传的 2012 年证书。但**不能只做这一条**（相机很可能强制 https）。建议：**E2 作为实验保留，产品默认走 TLS**，成功后再决定是否加入自动回退。请确认是否接受。

### D3. 相机端显示的应用名

原项目固定用 `'app'`。我倾向保守沿用 ASCII，**但如果你希望相机屏幕上显示中文应用名**（例如「间隔拍摄」），我可以在阶段 0 顺手验证相机的编码容忍度（低风险实验，失败就回退）。请选择。

### D4. 代码签名与分发

未签名的 exe 会被 SmartScreen 拦（"未知发布者"）+ 首次运行 Defender 扫描变慢。这属于发布环节，现在只需确认：**是否已有代码签名证书**？没有的话我会按"无签名 + 提供校验和/使用说明"的方式准备发布流程。

### D5. HTTP 服务器是否真的需要 axum / hyper（我建议**不要**）

你的原始要求里写了"HTTPS 服务器用 axum 或 hyper"。但读完源码后，我的结论是**这里不存在一个常规 HTTP 服务器**（理由见 §4.5）：没有路由、状态行是 `HTTP/1.0`、必须手写精确头部（还要故意用 SPK 的 MIME 冒充 JSON）、而且它跑在**一条由 USB 报文驱动的自定义字节管道**上而不是 `TcpListener::accept` 循环里——用 axum/hyper 还得额外把内存状态机伪装成 `AsyncRead/AsyncWrite`。

**建议：本期手写约 80 行的响应构造器**（`match method { GET => spk_bytes, POST => json_bytes }` + 头部拼装），把 hyper 留作将来若改走真 socket 时的备选。请确认是否接受这个偏离。

### 12.2 我独立验证过、与初判不同或有争议的结论

> 这一节请重点看：**其中两条是我在写作过程中推翻了自己的初判**，说明这个项目的"想当然"很容易出错。

| 结论 | 验证方式 | 结果 |
|---|---|---|
| "本地 HTTPS 服务器"其实是**USB 上的 TLS 隧道**，相机不走网络 | 读 `installer/__init__.py` 主循环 + `server.py` 绑定地址 | ✅ 确认 |
| ~~相机不校验证书~~ → **相机要求证书链能链到内置受信根 CA**，只是不校验有效期/吊销/主机名 | 原项目官方文档 `docs/AppInstallation.md:26` 原文："Only https connections signed by a known root CA are allowed. However, the certificate is still accepted if it is expired, revoked and for a different host." | ⚠️ **推翻我的初判**。推论：**必须继承捆绑证书，自签证书不可用** |
| ~~证书私钥是 RSA-1024~~ → **RSA-2048** | PKCS#1 DER 解析：modulus 字段 257 字节（含符号位 0x00）→ 2048 位；且必须与叶证书模数一致 | ⚠️ **推翻我的初判** |
| rustls 是否可用？ | 原项目 git 历史：提交 `a1c6a67f`（锁定 `PROTOCOL_TLSv1`）→ 提交 `9ab9dbe0`（因 OpenSSL ≥1.1.1 报 `CA_MD_TOO_WEAK` 而整栈换 `tlslite-ng`）；并核对 rustls 能力边界（不支持 TLS 1.0 / 静态 RSA 密钥交换 / SHA-1） | ❌ **rustls 很可能失败**；首选 `openssl` crate |
| 原实现有 keep-alive 吗？ | `server.py:20` 硬编码 `Connection: Keep-Alive`，但 `protocol_version` 未覆盖 → `HTTP/1.0` → CPython 置 `close_connection=True` | ⚠️ 实际**每请求关连接**，`Keep-Alive` 只是给相机看的 |
| SPK 的 AES 密钥可直接硬编码，**不需要 RSA 实现** | ① Python `pow(blob, 65537, n)` 复算；② Python 独立实现整套 SPK 打包，与 Rust 输出**逐字节比对** | ✅ `c301afd22ddba4c090eca46258e4bfb1`（3000 字节输入 → 3276 字节 SPK，两语言指纹同为 `3854cb10e657d532`） |

| 证书链只有叶 + 中间两级 | 枚举 PEM 里的 CERTIFICATE 块 | ✅ 2 个块，无根 |
| XPD 的 CIC 密钥长度 | 直接数字符：90 个十六进制字符 = **45 字节**（早期笔记误记为 60 字节，已更正；Rust 侧有长度断言锁住） | ✅ 45 字节 |
| PKCS#7 在每块内独立填充 | 读 `spk/util.py:4-7` 的 `pad()` + `chunk()` 组合 | ✅ 块密文 = 明文 + 16 字节 |
