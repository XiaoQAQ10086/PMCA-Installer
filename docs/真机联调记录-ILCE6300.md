## ⚠️ 一条重要的使用注意

**相机一旦有过未完成的任务，就会拒绝新的开始**：

```json
{"message":"Start not accepted","resultCode":10}
```

我试过自己发 `/task/complete` 替它收尾，相机回
`{"message":"Unknown request","resultCode":100}` —— **它不认我们拼的那条请求**。

所以办法只有一个：**拔插一次 USB 线复位**，然后重新运行。
程序现在会立刻给出这个提示并退出，不会让你对着"卡住"猜。

## 一、真机踩到的坑（按重要性排序）

### 坑 0：相机在等我们回应 `close_notify`（最后打通的那一关）

相机上传完设备信息后，会通过 TLS 发一个 `close_notify`，然后**等我们把连接收尾**。
我原先：

- **不回应** TLS 的 close_notify
- **不收尾**隧道（不发 `ProxyEnd`）

结果相机就一直干等，我们这边只看到"超时"，完全看不出问题在哪。

补上这两步之后，相机立刻继续：下载 → 安装 → 报成功。

```
[463] [TLS] ⚠️ 相机发来告警：close_notify
[463] [TLS] 回一个 close_notify 并收尾
[463] [隧道] 主动收尾 fd=15（发 ProxyEnd）
[473] [REST] 完成汇报：Successfully completed   ← 相机接着就去装完了
```

**教训**：TLS 告警和连接收尾**不是可选的礼貌动作**，它们是协议状态机的一部分。
把告警静默丢掉，就等于把相机给的信息和相机等你做的事一起丢了。

### 坑 1：TLS 记录**明文上限 16 KB**，超了相机直接拒绝

下载应用包时，响应是 147 KB，我把它塞进了**一条** TLS 记录。

RFC 2246 规定单条记录明文最多 `2^14 = 16384` 字节。相机收到超长记录后回：

```
[TLS] ⚠️ 相机发来告警：级别 2（fatal），描述 20（bad_record_mac）
```

**现象极具误导性**：告警说"MAC 校验错"，看起来像密钥推导有问题，
实际是**记录分帧**问题。这个坑让我在密钥上白查了一轮。

修法：把响应按 16384 字节切分，每片一条独立记录（各自的 MAC、序号、隐式 IV 链）。

### 坑 2：TLS 1.0 的填充长度**差一字节**（最隐蔽）

解开的客户端 Finished 长这样：

```
14 00 00 0c | 12 字节校验值 | 20 字节 MAC | 0b 0b 0b 0b 0b 0b 0b 0b 0b 0b 0b 0b
   Finished                                 └────── 12 个 0x0b ──────┘
```

按 PKCS#7 的习惯会认为"填充 11 字节"，但 **TLS 1.0 不是 PKCS#7**。

RFC 2246 §6.2.3.2 的结构是：

```
struct {
    opaque content[..];
    opaque MAC[..];
    uint8 padding[padding_length];   ← padding_length 个字节
    uint8 padding_length;            ← 再一个字节放长度值
}
```

并且明确写着：*"This length specifies the length of the padding field
**exclusive of the padding_length field itself**."*

也就是 **`padding_length` 的值不含它自己**，总共要剥掉 `padding_length + 1` 字节。

真机数据印证：`16(明文) + 20(MAC) + 11(填充) + 1(长度字节) = 48` ✅

**症状有多迷惑**：明文头部 `14 00 00 0c` 完全正确、校验值也正常，
只有**最后多出一个字节**，导致 MAC 永远对不上。
如果只看头部会以为密钥是对的、只是 MAC 算法错——方向完全跑偏。

**加密侧同理**：要补 `total_pad` 个字节，每个字节的值是 `total_pad - 1`。

### 坑 3：Finished 的校验值要**再套一层 PRF**

RFC 2246 §7.4.9：

```
verify_data = PRF(master_secret, finished_label, MD5(handshake_messages) + SHA1(handshake_messages), 12)
```

`MD5‖SHA1`（36 字节）只是 PRF 的**种子**，不是最终值。最终值固定 **12 字节**。

我一开始直接用了 `MD5‖SHA1`，而且**自己写的"假相机"测试还能通过**——
因为两端错得一模一样，互相验证不出问题。

另外两个细节：
- 标签要区分：客户端用 `"client finished"`，服务端用 `"server finished"`
- 转录要包含**双方来往的全部握手消息**（ClientHello + ServerHello + Certificate +
  ServerHelloDone + ClientKeyExchange），少一条都不行；
  但**不含 ChangeCipherSpec**（CCS 不是握手消息）

### 坑 4：XPD 的 CIC 密钥是**字符串本身**，不是解码后的值

原项目源码里写的是：

```python
cicKey = b'8595e68aa50d25dcc52b4d6e6a62af526efd7523a4cc47e212e82e979728d6f0dd02c7e4e79ddb317d56fea2bd'
```

这是 **Python bytes 字面量**，内容是 **90 个 ASCII 字符**，
**不是**把这段十六进制解码出来的 45 字节！

我误当成十六进制解码，相机直接回：

```json
{"message":"CIC hash mismatch","resultCode":300}
```

两个密钥算出的校验值完全不同：

| 密钥解释 | 对 `https://www.playmemoriescameraapps.com/` 的 CIC |
|---|---|
| ASCII 字符串（90 字节）**正确** | `281ae67024e41a14e76299d2ebee8d6e5c03bf527bdc38c0633a45a0d1988d37` |
| 解码成 45 字节（错误） | `c418bdfaecee4cfcd51d6b3bd85e2ca837f539d53d59ae967bf9341181e210d1` |

### 坑 5：HTTP 响应头与 JSON 必须**逐字节**照抄原项目

我一开始图省事做了几处"优化"，都成了可疑点：

| 我写的 | 原项目 | 说明 |
|---|---|---|
| `Connection: close` | `Connection: Keep-Alive` | 相机读这个头 |
| 没有 `Server` / `Date` | Python 的 `send_response()` 会补上 | 照抄 |
| 紧凑 JSON | `json.dumps` 在冒号/逗号后有空格 | 照抄 |
| 键按字母序 | **插入顺序** | `serde_json::Value` 用 BTreeMap 会重排键！ |

最后一项尤其隐蔽：`serde_json::json!` + `to_vec` 会把键按**字母序**排成
`{"args":…, "attrs":…, "command":…}`。任何 JSON 解析器都不该在意顺序，
但既然原项目的字节是确定的，就手写拼装，彻底消除这个变量。

验收方式是**与 Python 的输出逐字节比对**：安装指令两边都是 128 字节，完全相同。

### 坑 6：相机在普通 MTP 模式下**就能切换到安装模式**，不用去菜单里找

不用让用户在相机菜单里翻。原项目的做法是：**在 MTP 模式下**通过索尼私有命令
（`0x9280` 写）命令相机自己切换。

- 普通 MTP 模式（PID `077A`）：支持 `0x9280/0x9281/0x9282`
- 应用安装模式（PID `06A8`）：支持 `0x9488/0x9489/0x948c/0x948d`，
  厂商扩展变成 `sony.net/SEN_PRXY_MSG: 1.0;`

切换命令：命令组 `5`、命令号 `2`，不带正文、不读响应。

**注意**：相机重新插拔或休眠后会**复位回 MTP 模式**，
所以每次安装前都要检查并（必要时）重新切换（`install` 已自动处理）。

### 坑 7：MTP 读命令的三步**必须作为一个整体**，响应码要到第三步才有效

读数据的流程是三步：

```
1. EXECUTE_COMMAND_WITH_DATA_TO_READ  → 拿到上下文和总长度
2. READ_DATA                          → 读数据
3. END_DATA_TRANSFER                  → 结束传输
```

两个致命细节：

- **第一步返回的响应码恒为 `0x0000`，那不是错误。**
  MTP 的响应码要等**第三步结束后**才有意义。在第一步就检查会误判为失败。
- **第三步不是"可选收尾"，而是协议必需的一步。** 漏掉它传输没正常结束，
  相机也不会给出真正的响应码。

我一开始把三步拆成两个独立函数暴露出去，结果相机只回答了第一步的 `0x0000`，
看起来像"命令不被支持"。改成对外只有一个函数、内部走完三步后就正常了。

### 坑 8：代理消息头是 **56 字节**，不是 58

原项目按"42 字节填充"算出 58，但真机发来的是 **56 字节**：

```
00 00 01 00 81 b4 00 00 00 00 00 00 00 30 之后全 0
      ↑版本    ↑魔数    ↑dataSize=0    ↑读取标记 0x3000
```

字段**位置**与预期完全一致，只是尾部短 2 字节。
所以解析时只要够长、魔数到位就接受；我们该读的字段都在前 14 字节内。

### 坑 9：相机对请求的**回复也用 REST 方向标记 2**

原项目里 `REST_Out = 2`（"我们发出去的"），据此我一开始拒收方向为 2 的消息。
但真机上相机回我们的那条**也是 2**：

```
00 02 | 00 68 | "REST/1.0 200 OK\r\n..."
type=2  size=104
```

结论：**任何从相机收到的 REST 正文都当数据收**，不按方向标记过滤。

### 坑 10：相机的 JSON 回复可能带尾部填充，解析要宽松

相机的回复/汇报里可能带**尾部 0 字节或空行**（USB 传输补齐缓冲）。
用严格的 `serde_json::from_slice` 会失败，而且失败是**静默**的 ——
真机上我就是这样漏掉了"相机拒绝了 start"这个关键信号，白等了两分钟超时。

修法：解析前先裁掉尾部的空白与 0 字节。

### 坑 11：Windows 上用 C 薄封装比纯 Rust 手写 COM 可靠得多

Rust 手写 COM 绑定时，运行时读到的 vtable 指针有偏差，按下标取函数指针全部错位，
一调用就 `0xC0000005`。改用 C 之后编译器直接把问题指了出来：

```
error C2039: "SetGuidValue": 不是 "IPortableDeviceValues" 的成员
```

两个原因：
1. `IPortableDeviceValues` 的完整定义在 `PortableDeviceTypes.h`，
   `PortableDeviceApi.h` 里只有前向声明
2. 这些接口是 **C 风格**的（结构体只有 `lpVtbl`），必须定义
   `CINTERFACE` + `COBJMACROS`，或者用 `obj->lpVtbl->Method(obj, ...)`

另外两个构建细节：
- C 源码里有中文，MSVC 默认按 GBK 解析会报"字符串字面量中的换行符"，必须加 `/utf-8`
- 需要链接 `ole32` `oleaut32` `propsys` `PortableDeviceGUIDs`

## 二、最有价值的三条经验

1. **两端都由我实现的测试，只能证明"自洽"，证明不了"符合规范"。**
   坑 2、坑 3 都是这样漏过去的。真正抓住它们的是三类**外部基准**：
   真机录音回放、真机实测、与原项目独立实现逐字节比对。

2. **错误信息的字面含义可能把人带偏。**
   `bad_record_mac` 指向"密钥错"，实际是"记录超长"；
   `MAC 校验失败` 的真相是"填充长度差一字节"。
   遇到这类错误，第一件事是**把中间数据打出来看**，而不是顺着字面猜。

3. **不要把协议里的任何一步当成"可选的礼貌动作"。**
   `END_DATA_TRANSFER`、`close_notify`、隧道收尾 —— 漏掉任何一步，
   现象都只是"卡住"或"超时"，而原因离现象非常远。
