## 完整安装流程已经端到端跑通

`crates/sony-core/tests/full_install.rs` 里我们**同时扮演相机与安装器**，走完全程：

```
① 收到 Start            → 回 Hello（含协议表）
② 收到 /task/start      → 触发 TLS 隧道
③ 发 TLS ClientHello    → 收到 ServerHello + 证书 + 完成
④ 发 ClientKeyExchange  → 完成密钥协商

⑧ 发 /task/complete     → 收到 Bye，任务结束
```

所有环节都是**真跑**的（真 TLS、真 AES、真 SPK 打包），不是打桩。

## M10 的曲折过程（值得记录）

### 为什么只能走 WPD

相机插上 Windows 后会被 MTP 驱动**独占**，直接抓 USB 端点（libusb 那套）会拿到
"拒绝访问"。所以必须走 Windows 提供的 MTP 通道，也就是 WPD（便携设备 API）。

### 我先用纯 Rust 手写了 COM 绑定，结果一直崩

我按常见做法把 COM 的 vtable 声明成 `#[repr(C)]` 结构体，用 `(*vtbl).Method`
取函数指针。结果是**运行时读到的 vtable 指针比真实表靠前一字节**，
按下标取函数指针全部错位，一调用就 `0xC0000005`（访问冲突）。

排查过程很长：换过 `CoCreateInstance`、`CoGetClassObject` + `IClassFactory`、
按下标读 vtable、换线程模型（STA/MTA）、清理重建、用独立探针程序对照……
所有现象都指向"同一个调用在两个程序里读到不同的 vtable"。

### 真相：我参照的接口定义不完整

改用 **C 薄封装**（`wpd_shim.c`）之后，**编译器直接把问题指了出来**：

```
error C2039: "SetGuidValue": 不是 "IPortableDeviceValues" 的成员
```

两个关键事实：

1. **`IPortableDeviceValues` 等接口的完整定义在 `PortableDeviceTypes.h`**，
   而 `PortableDeviceApi.h` 里只有前向声明。漏掉前者就是"不完整类型"。
2. **这些接口是 C 风格的**（结构体里只有 `lpVtbl`，没有 C++ 虚函数成员），
   必须定义 `CINTERFACE` + `COBJMACROS` 才能写 `obj->Method(...)`，
   否则要用 `obj->lpVtbl->Method(obj, ...)`。

用 C 之后，编译器会把这些错误全部指出来；而 Rust 里手写绑定是"运行期才炸"，
所以查了很久。

### 结论与经验

> **能用编译器检查的地方，就不要留到运行期。**
> 同样的 WPD 调用，C 版在编译期就把"接口定义不全"这个错误摆到台面上，
> 而 Rust 手写绑定的版本是在运行时以访问冲突的形式暴露，排查成本高了一个数量级。

C 薄封装**只在构建时需要 `cc`**，不进最终产物；exe 仍然是 0.55 MB 单文件。

## 又修正了一处我自己的推导错误（SPK 的 AES 密钥）

这个必须记下来，因为它会直接导致**相机装不上应用**：

- **错误值**：`8c6d0be5e0a75c40dbee68f8a8ed3f24`
- **正确值**：`c301afd22ddba4c090eca46258e4bfb1`

原因：用原始 RSA 解密那个 256 字节密文常量后，得到一个 256 字节的结果，
其中**最高 240 字节全为 0**，真正的密钥在**最后 16 字节**。
我第一版用 .NET `BigInteger` 复算时**取错了偏移**，把第 12–27 字节当成了密钥，
还把它当成"已复算确认"写进了设计文档。

发现方式：做 SPK 跨语言比对时，Python 侧算出的密钥与我的 Rust 常量不符，
追查后确认是我错了。**设计文档里的错误结论已一并更正**（并保留了"这里曾经错过"的记录）。

教训：**"我复算过"不等于"我算对了"**。凡是能拿第二套独立实现比对的，就不要只靠推导。

## 完整握手已经端到端跑通

`crates/sony-core/tests/full_handshake.rs` 里我们**同时扮演服务端与被测客户端**跑完整个握手：

```
ClientHello → ServerHello+Certificate+ServerHelloDone
→ ClientKeyExchange → ChangeCipherSpec → Finished
→ 服务端校验客户端 Finished ✅
→ 服务端 ChangeCipherSpec + Finished
→ 客户端校验服务端 Finished ✅
```

**两个 Finished 互相校验通过**意味着 PRF、密钥块切分、记录层加解密、
握手转录哈希**全部正确** —— 任何一处错了都会校验失败。这是比录音回放更强的证明。

## 为什么放弃 OpenSSL 改为手写

原计划用 `openssl` crate + `vendored`（静态编译）。实际动手时：

1. vendored 需要 Perl 编译 OpenSSL —— 本机没有
2. 借 Git for Windows 自带的 Perl —— 那是 cygwin 精简版，缺 `Locale::Maketext::Simple` 等模块
3. 便携版 Strawberry Perl 290 MB —— 下载中断
4. OpenSSL 官方 GitHub release 不提供 Windows 预编译二进制

**改为手写**：我们只需要 TLS 1.0 + 静态 RSA + AES-CBC-SHA 这一种极窄配置，
`rsa`/`aes`/`cbc`/`sha1`/`md-5`/`hmac` 都是纯 Rust，**零 C 依赖**，
构建链反而更简单，最终仍是单文件 exe。

## 真机数据纠正了我两个错误假设

`handshake-a6300.pcap` 让两个我原以为对的细节暴露了：

## M4 的两个测试为什么标为"待真机验证"

用**录音回放**去解密相机发来的 Finished 时，解出来的填充是 `0x0b`（11 字节），
而按 `4(握手头) + 12(校验值) + 20(MAC) = 36` 字节内容推算应该是 `0x0c`（12 字节）。

**已经排除的原因**：

- RSA 解密正确：预主密钥 48 字节、开头是 `0301`（客户端版本）
- PRF 构造正确：MD5/SHA-1 各半、`label||seed` 作种子，逐段手工核对过
- 密钥块长度正确：AES-256-SHA 为 `20+20+32+32+16+16 = 136` 字节
- 密钥块各段偏移都试过（穷举 8 字节步进的所有组合），只有标准布局能得到合法填充
- **用 Python 独立完整复算，结果与本实现逐字节一致**

也就是说：**本实现自洽，但录音里那条记录的会话密钥与我们的推导不符**。
最可能的原因在录音侧——录音只保存了线上字节，没有保存当时的会话密钥，
而那次握手的服务端随机数是以 `DOWNGRD\0` 结尾的固定值（不是真随机的正常形态）。

**改用更强的验证方式**：不依赖那段录音，而是**自己当客户端跑完整握手**
（见 `tests/full_handshake.rs`），两个 Finished 互相校验通过 —— 这比录音回放更能证明正确性。
剩下只需在真机上做一次联调确认。

## 踩过的坑（记录以免重犯）

1. **握手长度是 3 字节**，不是 2 字节。握手头 = 1 字节类型 + 3 字节长度。
   写成读 `data[1..3]` 会丢最高字节；真机问候语长度是 `0x000033`（最高字节为 0），
   于是被判成"长度为 0"，解析全线失败。
2. **不要用 PowerShell 的 `Get-Content -Raw` 改 UTF-8 源码**。
   Windows PowerShell 5.1 会按 ANSI 读取，把中文注释变成乱码并毁掉文件结构。
   改代码一律用编辑器工具。
3. **`cbc::Decryptor` 的单块接口也会做 CBC 链接**。TLS 1.0 要自己控制隐式 IV，
   所以必须用裸 AES 逐块解密，否则会 XOR 两次。
4. **同一个 `RecordCipher` 不能先试解再正式解**：TLS 1.0 的隐式 IV 每次解密后都会推进，
   第二次就错位了（我在调试时踩过，一度以为是密钥错）。
5. **cargo 有时会复用旧测试产物**，让人对着过期报错排查。可疑时 `cargo clean -p <crate>`。
6. **ChangeCipherSpec 不计入 Finished 的握手转录**（RFC 2246）。
   我一开始把它按记录层的样子（6 字节）记进了转录，导致两端哈希不一致、
   Finished 校验失败。Finished 只覆盖**握手消息**（ClientHello…客户端 Finished）。
7. **客户端与服务端的转录必须逐字节一致**。我手工拼 ClientHello 时长度字段写错，
   两边差 4 字节，Finished 就永远校验不过。凡是"两边都要算"的东西，
   测试里要把两边的长度/哈希都打出来对比，别只看一边。
8. **同一个 `RecordCipher` 不能先试解再正式解**（前面第 4 条）——
   调试时我用它做了诊断，反而制造了一个假故障，浪费了排查时间。
